# RE:STATIC team

Astro в серверном режиме на Node.js, Tailwind, PostgreSQL, Drizzle ORM и Better Auth. Лендинг — RU/EN/KO/JA; кабинеты заказчика, исполнителя, модератора и администратора — RU/EN.

## Что работает

Заявки AMV, GMV, GFX, LOGO, VIDEO CLIPS и OTHER; согласование ТЗ; подтверждение исполнителя; версии предложения; оплата; закрытые файлы и видео с перемоткой; общий чат и внутренние заметки; два раунда творческих правок; отправка превью/финала; приёмка; заработок; резервирование и ручная выплата. Исправления подтверждённых несоответствий ТЗ не расходуют творческие раунды.

Роли совмещаются в одном аккаунте. До оплаты исполнитель получает краткое ТЗ, после оплаты — материалы и чат своего заказа. Модератор сопровождает заказ, администратор дополнительно управляет пользователями, ростером, портфолио, ценами, возвратами и выплатами. Условия конкретного предложения можно скачать из заказа; их снимок сохраняется независимо от последующих правок сайта.

Случайный подбор учитывает специализацию, доступность, подтверждённый аккаунт, процент и занятость. Один активный заказ на исполнителя, включая приглашения и принятые неоплаченные заявки. OTHER назначается вручную, замена предпочтительного исполнителя требует подтверждения клиента. Приглашение на заказ действует 24 часа, предложение — 7 дней. После истечения требуется повторное подтверждение. Запоздалая оплата попадает на проверку администратора; при невозможности продолжить заказ администратор возвращает деньги через Robokassa и фиксирует возврат.

Завершение и начисление не повторяются при повторном запросе. Молчание клиента не означает автоматическую приёмку. Результат публикуется в портфолио только с отдельным разрешением клиента; отзыв разрешения скрывает публикацию.

## Локальный запуск

Нужны Node.js 22.12+ и Docker. Используйте npm и `package-lock.json`.

```sh
npm ci
cp .env.example .env
```

В `.env` задайте `POSTGRES_PASSWORD` и такую же парольную часть `DATABASE_URL`. Для пароля базы удобно использовать случайную строку из шестнадцатеричных символов, чтобы не экранировать её в URL. Задайте независимые случайные значения `BETTER_AUTH_SECRET` и `DATA_SECRET`, минимум 32 байта каждое. Генератор одного значения: `openssl rand -hex 32`. Не добавляйте `.env` в Git.

Для локальных писем установите `SMTP_HOST=127.0.0.1`, `SMTP_PORT=1025`, `SMTP_SECURE=false`, `SMTP_FROM=noreply@restatic.test`. Авторизация SMTP для Mailpit не нужна.

```sh
docker compose --env-file .env -f compose.dev.yml up -d
npm run db:migrate
npm run db:seed
npm run dev
```

В другом терминале запустите `npm run worker`. Сайт: `http://localhost:4321/ru/account/`. Локальный почтовый ящик Mailpit: `http://127.0.0.1:8025` — письма никуда наружу не отправляются.

При отсутствии DATABASE_URL лендинг может показывать исходное портфолио и ростер; кабинету требуется настроенная база. При настроенной, но недоступной базе приложение возвращает ошибку, вместо подмены данных заглушкой.

### Первый администратор

Первый владелец — `hikeru1@icloud.com`, переопределяется `OWNER_EMAIL`. Перед созданием задайте временный уникальный `ADMIN_INITIAL_PASSWORD` длиной от 16 символов в локальной `.env`:

```sh
npm run admin:create
```

Удалите временный пароль из `.env` после создания. Команда создаёт подтверждённый аккаунт и роль администратора, но отказывается повышать права уже существующего аккаунта с тем же email. Общего или встроенного пароля нет. Если аккаунт уже существует, используйте восстановление доступа либо проверенное административное исправление в БД.

Участников приглашайте из админки по реальному email. Получатель регистрируется/входит с этой почтой и принимает приглашение. Приглашение на аккаунт действует 7 дней. Затем задайте специализации и процент; исполнитель сам открывает доступность в кабинете. Начальное заполнение добавляет 29 участников и 12 работ, без аккаунтов, вымышленных email, процентов и авторства. `torro` изначально не участвует в подборе. Повторный seed не перезаписывает изменения админки. Цены изначально «по согласованию».

## Dokploy

1. Создайте сервис Docker Compose, подключите GitHub-репозиторий и выберите `docker-compose.yml`.
2. В Environment внесите значения из `.env.example`. Для сервера используйте `APP_URL=https://restatic.team`. `DATABASE_URL` в Compose формируется автоматически с хостом `database`; значение localhost из примера для сервера не требуется.
3. Обязательно задайте POSTGRES_PASSWORD, BETTER_AUTH_SECRET и DATA_SECRET. Сохраните секреты: DATA_SECRET нужен для расшифровки реквизитов выводов после восстановления.
4. Настройте SMTP с реальным адресом отправителя и параметрами провайдера. Подтверждение почты, восстановление пароля и приглашения требуют работающей доставки писем.
5. Deploy. Миграции и повторяемый seed запускаются перед приложением. Worker ждёт healthy приложения, затем отправляет письма, обрабатывает истечения сроков, напоминания и итоговые чеки.
6. В Domains укажите домен restatic.team, сервис `frontend`, порт `3001`, путь `/`, HTTPS. Создайте A-запись на IP сервера. Внешнюю сеть `dokploy-network` создаёт Dokploy.
7. Создайте первого администратора из терминала контейнера frontend. Запустите `sh`, введите пароль с выключенным отображением, выполните команду и удалите переменную:

```sh
stty -echo
read -r ADMIN_INITIAL_PASSWORD
stty echo
export ADMIN_INITIAL_PASSWORD
npm run admin:create
unset ADMIN_INITIAL_PASSWORD
exit
```

Снаружи доступно только приложение через Traefik. PostgreSQL не публикует порт. Постоянные тома: `database-data` и `order-files`; файлы хранятся в `/data/files`, вне public. Не удаляйте тома при Redeploy и не используйте `down -v` на рабочем проекте.

Compose проверяет здоровье PostgreSQL, приложения `/api/health/` и heartbeat worker. SMTP/Robokassa нужны исходящие сетевые соединения. Worker использует блокировку PostgreSQL, поэтому два экземпляра не отправляют одну очередь одновременно. Ошибки SMTP повторяются с задержкой и не отменяют уже выполненное действие в заказе.

Если добавляете свой reverse proxy/CDN, разрешите потоковые запросы размером **1 GiB + 256 KiB**, достаточный таймаут загрузки и Range-запросы. Ограничение самого файла остаётся 1 GiB, материалов одного заказа — 20 GiB. Приложение принимает видео, аудио, изображения, PDF/DOCX/TXT и ZIP/7Z/RAR, проверяет расширение и содержимое; большие исходники передаются ссылками. Не подключайте стороннюю публичную раздачу тома order-files.

### Robokassa и чеки

По умолчанию `ROBOKASSA_TEST=true`, `PAYMENTS_LIVE_READY=false`. Укажите логин магазина, тестовые Пароли №1/№2, выбранный в магазине алгоритм подписи `ROBOKASSA_HASH` и параметр НДС `ROBOKASSA_VAT`. НДС не выводится автоматически из УСН. УСН «Доходы» передаётся как `usn_income`.

В магазине настройте:

- ResultURL: `https://restatic.team/api/payments/result/`, метод POST.
- SuccessURL: `https://restatic.team/ru/account/`, метод GET.
- FailURL: `https://restatic.team/ru/account/`, метод GET.

Возвращение браузера не подтверждает платёж: только ResultURL с проверенными подписью, номером, суммой и привязкой к заказу. Сумма формируется из сохранённого предложения на сервере. Повторный ResultURL не создаёт повторного начисления. Рабочие и тестовые платежи, начисления и выводы разделены; тестовые выводы не требуют реального перевода денег.

При оплате передаётся чек полной предоплаты. После завершения worker отправляет чек зачёта через RoboFiscal и проверяет его регистрацию; ошибки видны в админке. Кнопка повторной проверки запрашивает статус уже отправленного чека, не создаёт ещё один чек. Возврат в первой версии выполняется вручную в Robokassa; запись в кабинете требует суммы и подтверждения, корректирует заработок. Чеки возврата и разбор ошибок фискализации выполняйте через Robokassa.

Для рабочего режима настройте магазин и Робочеки, подтвердите НДС, проведите реальный тест интеграции с магазином, затем задайте рабочие Пароли №1/№2, `ROBOKASSA_TEST=false` и `PAYMENTS_LIVE_READY=true`. Локальные автоматические тесты имитируют подписанный ResultURL и **не подтверждают** работу самого магазина или реальную регистрацию чеков.

## Проверки

```sh
npm run check
npm run build
npm test
npm run test:prepare
npm run test:integration
```

`test:prepare` создаёт игнорируемую Git `.env.test` на основе локальной `.env`, переключает её на отдельную `restatic_test`, Mailpit и случайные фиктивные ключи платежей. Тесты требуют работающего локального PostgreSQL и Mailpit. Интеграционные тесты очищают **только** БД с суффиксом `_test`; не подключайте их к рабочей базе. Они запускают собранное приложение на 4322.

Для браузера один раз установите Chromium:

```sh
npx playwright install chromium
UI_TEST=true npm run test:integration
LARGE_UPLOAD_TEST=true UI_TEST=true npm run test:integration
```

Проверяются регистрация/подтверждение/восстановление, роли, приглашения, конкурентные назначения и выводы, подписанные/поддельные/повторные платежи, просроченная оплата, закрытые Range-запросы, два раунда правок и исправления, приёмка, начисления, выплаты, возвраты, согласие на публикацию, истечения, SMTP, RU/EN и мобильная ширина. LARGE_UPLOAD_TEST дополнительно передаёт 1 GiB и 1 GiB + 1 байт, проверяет границу размера и удаляет большой тестовый файл.

## Миграции и резервное копирование

Схема: `src/server/db/schema.ts`, SQL и журнал версий: `drizzle/`. При изменении схемы выполните `npm run db:generate`, проверьте SQL, затем `npm run db:migrate`. Не используйте `drizzle-kit push` для рабочей базы. Миграции применяются последовательно под блокировкой; seed не дублирует записи. Изменения ростера, цен и портфолио читаются из БД без пересборки сайта.

Резервная копия должна включать БД, файлы, конфигурацию секретов и Git-ревизию образа. Для согласованной копии остановите приложение и worker, оставив PostgreSQL работающим. Пример из каталога проекта с доступной `.env`:

```sh
task_backup_dir="backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$task_backup_dir"
chmod 700 "$task_backup_dir"
docker compose stop frontend worker
docker compose exec -T database sh -c 'pg_dump -Fc -U "$POSTGRES_USER" "$POSTGRES_DB"' > "$task_backup_dir/database.dump"
docker compose run --rm --no-deps --entrypoint tar frontend -C /data/files -czf - . > "$task_backup_dir/files.tar.gz"
git rev-parse HEAD > "$task_backup_dir/revision.txt"
cp .env "$task_backup_dir/environment.env"
chmod 600 "$task_backup_dir"/*
docker compose start frontend worker
```

Если секреты хранятся в Dokploy вместо `.env`, отдельно сохраните их в защищённом хранилище. Храните копии вне сервера и проверяйте восстановление. Каталог backups исключён из Git и Docker-контекста.

### Восстановление

Проверьте восстановление в **отдельном** проекте с пустыми томами, той же версией PostgreSQL и соответствующей Git-ревизией. Восстановите конфигурацию, включая исходный DATA_SECRET. Запустите только database и дождитесь healthy:

```sh
docker compose up -d database
docker compose exec -T database sh -c 'pg_restore --clean --if-exists --no-owner -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < /path/to/database.dump
docker compose run --rm --no-deps -T --entrypoint tar frontend -C /data/files -xzf - < /path/to/files.tar.gz
docker compose up -d frontend worker
```

`pg_restore --clean` заменяет содержимое целевой БД, поэтому целевой проект должен быть выделен под восстановление. Перед возвращением трафика проверьте вход, состав команды, заказы, закрытые файлы, суммы и очередь писем. Откат приложения после миграции делайте через соответствующую резервную копию, если старая версия несовместима с новой схемой.

## Серверные маршруты и структура

Все изменения проверяют сессию, подтверждение почты, роль, доступ к заказу, состояние и Origin на сервере. Денежные операции и подбор сериализуются блокировками БД. Авторизация Better Auth находится под `/api/auth/`; собственные API возвращают JSON и коды ошибок. В URL API сохраняйте завершающий `/`, особенно для POST.

| Маршрут | Назначение |
| --- | --- |
| `/api/me/`, `/api/catalog/` | Аккаунт, общие работы/цены/команда |
| `/api/orders/`, `/api/orders/:id/` | Создание, списки, детали и разрешённые действия заказа |
| `/api/orders/:id/terms/?quote=:id` | Сохранённая редакция условий предложения |
| `/api/orders/:id/checkout/`, `/api/payments/result/` | Оплата и подписанное уведомление |
| `/api/orders/:id/files/`, `/api/files/:id/` | Потоковая загрузка и закрытая раздача |
| `/api/availability/`, `/api/finance/`, `/api/withdrawals/` | Доступность, заработок, запрос вывода |
| `/api/notifications/`, `/api/claim/` | Уведомления и принятие приглашения |
| `/api/admin/data/`, `/api/admin/{members,portfolio,rates,users,invite}/` | Управление данными и доступом |
| `/api/admin/finance/`, `/api/admin/withdrawals/`, `/api/admin/receipts/` | Выплаты, финансовый обзор, проверка чеков |
| `/api/media-upload/`, `/api/public-media/:id/` | Медиа портфолио; опубликованность и согласие проверяются перед выдачей |
| `/api/orders/:id/refund/` | Учёт фактически выполненного возврата администратором |

Общие типы — `src/shared/types.ts`; бизнес-процессы — `src/server/services/`; очередь — `src/server/worker.ts`; интерфейс — `src/components/cabinet/Portal.astro` и `src/client/portal.ts`.

Юридические страницы — `src/data/offers.json`, `src/data/privacy.json`; оферты для скачивания — `public/documents/`. При новой редакции синхронно обновляйте JSON, DOCX, дату LegalPage и termsVersion; принятые снимки в заказах не изменяются. Форма собирает страну клиента и отдельно фиксирует запрос начать работу после оплаты. Без запроса заказ ожидает разрешения на начало; модератор фиксирует основание с учётом применимого срока отказа и необходимых отдельных подтверждений по п. 7.4 оферты. Система не определяет применимое право автоматически.
